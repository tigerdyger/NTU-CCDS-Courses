## 2. 严格偶数 PID 优先

### 策略与实现

每次新选择都先扫描 `RUNNABLE` 的偶数 PID；只有整轮找不到，才扫描奇数。选择后仍沿用原版的状态赋值、`c->proc` 设置、上下文切换及锁交接。

切回调度器后，先释放当前进程锁，再结束扫描，重新从偶数优先开始。不能扫描完偶数后持续调度多个奇数而不重新检查偶数，否则会使用过时的“没有偶数就绪”判断。

这里保留时钟抢占。同一优先级内从表头开始、选第一个符合条件的进程，不保证该类内部公平，也不是 round robin（轮转）。因此有限测试中出现一个进程打印完四轮后另一个才打印，不等于抢占失效：抢占后可能仍然选中同一个进程。

### 两个测试各说明什么

| 测试 | 工作负载 | 能支持的结论与限制 |
| --- | --- | --- |
| `schedtest` | 四个子进程各做四轮有限计算，再退出 | 比较实际执行输出；子进程最终退出，因此不能单独证明无限饥饿 |
| `starvetest` | 一奇一偶两个子进程通过管道同步后无限计算，不主动睡眠、输出或退出 | 在单核下结合严格策略说明奇数可能无限等候；有限 Ctrl-P 快照本身只证明采样时刻的状态 |

课程源码的 `schedtest.c` 是 `WORK=40000000`，手册对应文字写 4,000,000；本次保留提供的源码，不为匹配文字擅改计算量。管道同步和打印也可能导致阻塞，不能默认每条输出之间所有子进程始终就绪。

原版快照中分别观察到两种 PID 运行；修改版三次均为偶数运行、奇数就绪。长期饥饿的推理是：偶数无限计算、没有主动阻塞，并在每次让出后重新就绪；每次优先级选择都会先选偶数，因此奇数可以无限得不到 CPU。

测试使用 `CPUS=1`。三核时，一个偶数进程若已在另一核处于 `RUNNING`，就不是本核扫描的 `RUNNABLE` 候选，不能直接照搬单核饥饿结论。无限循环用 QEMU 的 Ctrl-A、X 结束，不依赖可能得不到 CPU 的 shell 执行 kill。

## 3. 用户线程的保存状态

这些线程共享同一个 xv6 进程的地址空间；每个线程有独立的栈和 saved context（保存的上下文）。内核调度的是这个进程，库在 `thread_yield()` 或 `thread_exit()` 时切换用户线程。改成三核不会让这几个用户线程各自占一个核并行运行。

| 字段 | 汇编偏移，单位为 byte（字节） |
| --- | --- |
| `ra` | 0 |
| `sp` | 8 |
| `s0`、`s1` | 16、24 |
| `s2` 至 `s9` | 32、40、48、56、64、72、80、88 |
| `s10`、`s11` | 96、104 |

上下文共 14 个 64-bit 字段，即 112 字节。偏移从 context 的地址开始算，不是从包含栈数组的 `struct thread` 开头算。

切换发生在普通函数调用边界：`s0--s11` 是 callee-saved registers（被调用者保存寄存器），调用者会按 ABI 处理仍需使用的 caller-saved registers（调用者保存寄存器）。`ra` 本身不是普通调用约定中的 callee-saved 寄存器，但切换必须额外保存它和 `sp`，以恢复正确的执行位置和栈。与任意指令处的时钟陷阱不同，这里不需要为每个用户线程新建一份完整 trapframe。

## 4. 新线程与恢复线程

### 初始上下文

`thread_create()` 找到空闲槽位，清零上下文，再设置：

- `ra` 为入口函数地址；
- `sp` 为自己栈的高地址端，并通过清除最低四位向下对齐到 16 字节；
- 完成初始化后标为 `RUNNABLE`。

栈向低地址增长。仅凭 `STACK_SIZE=8192` 是 16 的倍数，不能保证结构体数组内每个栈顶地址都对齐，因此仍需对指针显式对齐。

本次另有“没有空闲槽位则报错退出”的保护。测试入口函数都显式调用 `thread_exit()`；代码未提供入口函数普通 return 后自动退出的通用 trampoline（跳板）。

### 一次线程切换

```text
旧线程调用 thread_yield()
  -> 标为 RUNNABLE
  -> thread_schedule() 选择新线程并标为 RUNNING
  -> thread_switch(&旧context, &新context)
       a0 指向旧context，sd 保存旧寄存器
       a1 指向新context，ld 恢复新寄存器
       ret 使用恢复后的 ra
  -> 新线程首次进入函数，或恢复到它先前的调用位置
```

`current_thread` 更新前，要用 `t` 保留旧线程指针。恢复的是已经暂停的线程时，它会从以前的 `thread_switch()` 调用之后继续，而不是从入口重新执行。

`thread_exit()` 将自己标为 `FREE` 后调度，之后不应再被当成就绪线程选中。提供的测试 main 也调用 `thread_exit()`，让主线程退出用户库的调度。

## 5. 结果与排错

两次测试的可见尾部都以 c、a、b 的顺序交替推进至 99，三个线程各打印 `exit after 100`，最后为：

```text
thread_schedule: no runnable threads
```

这是本测试线程全部结束后的预期提示；库内部随后调用 `exit(-1)`，并非操作系统崩溃。测试函数启动后会等待另外两个线程也启动，所以开始计数的顺序不必与创建或打印 started 的顺序相同。

| 现象 | 重点检查 |
| --- | --- |
| 未实现版无输出 | 原始基线的预期行为，不能当成实现成功 |
| `invalid type argument of '->' (have 'int')` | 本次实际笔误为把 `&t->context` 写成 `&4->context`；修正后编译通过 |
| 只有一个线程启动或切不走 | 切换调用、传入地址、初始 `ra` 及可运行状态 |
| 切换后崩溃或计数异常 | C 字段与汇编偏移、保存的寄存器、独立栈及 16 字节对齐 |
| 已退出线程再次运行 | `FREE`、`RUNNABLE` 的状态转换与扫描条件 |

原始代码快照仍有已经实现的 `TODO` 注释，它们只是未清理的注释，不代表对应逻辑缺失；整理时仅清理行尾空白，不改写已测试的代码逻辑。

## 一分钟回顾

- `RUNNABLE` 是可被调度，`RUNNING` 是正在执行；策略改变选谁，不能破坏切换机制。
- kernel context、trapframe 和用户地址空间不是同一个东西。
- 偶数严格优先可以使奇数饥饿；有限快照要与代码和负载条件结合解释。
- 用户线程通过函数调用协作切换，保存 `ra/sp/s0--s11`；字段顺序必须与汇编偏移一致。
- 第一次运行依赖构造的入口地址和对齐栈，恢复运行依赖先前保存的真实上下文。
