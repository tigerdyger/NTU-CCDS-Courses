# Part 1：Spinlock 与 Sleep/Wakeup 的源码路线

来源：Lab 3 Manual PDF pp. 4–5，以及 [README 中固定的课程源码快照](README.md#来源)。本部分阅读原有实现，不修改 `spinlock.c` 或 `proc.c`。

## 1. Acquire 与 Release 各自保证什么

`kernel/spinlock.c` 中的 `acquire(lk)` 依次完成：

1. `push_off()`：关闭当前 CPU 的中断，并维护嵌套计数。这样持锁期间不会因同一 CPU 上的中断处理再次争用该锁而自锁；它不能阻止其他 CPU 访问共享数据。
2. `__sync_lock_test_and_set(&lk->locked, 1)`：原子地读取旧值并写入 1。旧值为 0 的调用者获得锁；其他 CPU 继续自旋。
3. 内存屏障：限制编译器和处理器对临界区内存操作的重排。
4. 记录持锁 CPU，供调试和持锁检查使用。

`release(lk)` 检查锁的所有者，清除所有者记录，经内存屏障后原子释放锁，最后 `pop_off()` 恢复对应的中断嵌套状态。不能把解锁放在临界区写操作之前。

单独的“先读 `locked`、发现 0、再写 1”不是 test-and-set：两个 CPU 都可能先读到 0，随后同时进入临界区。跨 CPU 互斥依赖原子操作，不是仅靠关中断。

## 2. Sleep 为什么不能简单地先解锁再睡眠

等待者在条件锁保护下发现资源不可用。如果直接解锁，再设置自己的睡眠状态，就存在空隙：另一个进程可能先更新条件并调用 `wakeup()`，当时等待者尚未标记为睡眠；它随后睡下，错过这次唤醒。这就是 lost wakeup（丢失唤醒）。

`kernel/proc.c` 的 `sleep(chan, lk)` 使用两把不同的锁交接：

| 顺序 | 等待进程的操作 | 保证 |
| --- | --- | --- |
| 进入函数 | 已持有条件锁 `lk` | 检查条件与决定等待受同一把锁保护 |
| 交接 | 先获取自己的 `p->lock`，再释放 `lk` | 不留下唤醒者可错过睡眠登记的空隙 |
| 登记 | 设置 `p->chan = chan`、`p->state = SLEEPING`，调用 `sched()` | 进程状态与等待通道受 `p->lock` 保护 |
| 恢复 | 重新被调度后清空 `chan`，释放 `p->lock`，重新获取 `lk` | 返回调用者时仍持有条件锁，可以再次检查条件 |

其中 `chan` 只是标识等待条件的地址，不是消息内容，也不需要另外创建一个队列。在本实验中用 semaphore 对象的地址作为通道。

更新条件的进程持有同一个条件锁，修改资源状态，再调用 `wakeup(chan)`。`wakeup()` 扫描进程表，逐个取得 `p->lock`，把匹配通道的 `SLEEPING` 进程改为 `RUNNABLE`。它并不立即切换到该进程，更没有保证资源已经归该进程所有。

## 3. 为什么必须用 While 重新检查

同一通道上的多个等待者可能一起被唤醒，但增加的可用资源可能只有一个。它们重新获得条件锁时，前一个进程可能已经消耗资源，所以等待必须写成：

```c
while (sem->value == 0) {
  sleep(sem, &sem->lock);
}
```

只有再次检查到 `value > 0`，才在仍持锁的情况下减一。把 `while` 改成 `if` 会让后来恢复的进程跳过复查，可能消耗不存在的许可。

## 4. 自旋与阻塞适用的场景

Spinlock 适合很短的内核临界区；等待时占用 CPU，但不需要完整的睡眠和调度切换。Blocking semaphore（阻塞信号量）适合资源可能较久不可用的情况，等待者让出 CPU，代价是调度开销。

手册中的等待周期数是用于比较的假设，不是本次测出的性能阈值。不能简单把“自旋快”或“阻塞省资源”当成任何场景下的结论。

本实验的 semaphore 在修改 `value` 时短暂持有内部 spinlock；资源不可用时，`sleep()` 按上述协议释放这把锁再调度。因此“用 spinlock 实现 semaphore”不等于“持着 spinlock 一直等待资源”。
